#+title: org-truss
#+options: toc:2

Build an argument of members joined into trusses, and make an output
document of it, in Org.

It needs [[https://github.com/yoshzucker/org-dock][org-dock]], which takes a
heading out to be written in, and
[[https://github.com/yoshzucker/org-item-tags][org-item-tags]], which gives an
item of a list tags as a heading has, and works with
[[https://github.com/yoshzucker/org-moor][org-moor]], for the sources read,
when it is there.

* Why

A truss carries load because its members are joined into triangles.  A
member on its own is just a length of steel; whether it is a chord or a
diagonal depends on where it is placed.  And the same members can be framed
in more than one way -- a Warren truss, a Pratt truss -- for the same span.

A document that argues for something works the same way.  A statement on its
own is only a statement; it becomes the situation, or the grounds, or the
conclusion, by where it is placed.  A claim stands only if something is
under it.  And the same statements can be arranged as fact, interpretation,
action, or as an answer followed by its reasons.

So this package keeps three things apart:

- *members* -- every statement, written once
- *patterns* -- what the members right under a member are to it: its
  reasons, its breakdown, and the order they are told in
- *Structure* -- the output document's outline, which includes the
  members it carries

Structure can be rearranged as often as you like without touching a
member, and the board says, at every point, which reasons have no
grounds, which roles a pattern asks for that nothing plays, and what is
taken as given.

The way an argument is built here follows Paul Graham's bottom-up
programming, carried from programs over to prose: Subject is the language
the sources give, Message the words built up from it toward what the
document has to say, written down from that end at once, and Structure
the document written in them.  See Paul Graham, "Programming Bottom-Up"
(1993), and /On Lisp/ (1993): 1.1 "Design by Evolution", 1.2
"Programming Bottom-Up", 4.1 "Birth of a Utility", 4.2 "Invest in
Abstraction" and 4.8 "Density".

Nothing here needs a language model.  The file is meant to be filled by hand;
a model can help fill it, but the structure is yours.

* The model

** Words

The guide at the head of every truss file (see [[*The guide]]) defines these
words, and the board, the checks and this README use them alone.

| Word            | What it is                                                                                                  |
|-----------------+-------------------------------------------------------------------------------------------------------------|
| pattern         | what a heading or an item says the ones right under it are to it: ~:logic~, ~:breakdown~, ~:telling~                |
| role            | what one right under plays in the pattern above: /reason/, /who/, /sky/                                       |
| member          | one heading, or one item of a list marked ~#+attr_truss~                                                     |
| truss           | a member with a pattern (its /apex member/) and the members right under it (its /supporting members/)        |
| end member      | a member with no pattern; it has nothing under it                                                            |
| simple truss    | a truss whose supporting members are all end members; =△= on the board                                      |
| compound truss  | a truss with an apex member among its supporting members; =▲= on the board                                  |
| ID              | the name a member is pointed to by: ~<<m7>>~ in its words, a heading's or an item's; a ~CUSTOM_ID~ too      |
| pointing link   | ~[[m7]]~, or ~[[#m7]]~: points to m7 as grounds                                                             |
| include link    | ~[[truss-include:m7]]~: includes m7 there in the output document, the whole truss when m7 is an apex member  |
| axis            | what a breakdown is cut by, ~TRUSS_BY~ or ~:by~: its supporting members are all there is                    |
| value           | what a member is under an axis: the term before ~::~, or its words                                          |
| output document | what the file is written out as, in ~out/~                                                                   |

** Four divisions

| Division  | What it holds                                                                          | Where                       |
|-----------+----------------------------------------------------------------------------------------+-----------------------------|
| Brief     | the reader, and what the output document must satisfy                                  | ~TRUSS_DIVISION: brief~     |
| Subject   | the facts found: one truss for each source                                             | ~TRUSS_DIVISION: subject~   |
| Message   | what the output document says: what the facts mean, and what to do                     | ~TRUSS_DIVISION: message~   |
| Structure | the output document's outline, built of trusses, its text holding the include links   | ~TRUSS_DIVISION: structure~ |

Each division is found by its ~TRUSS_DIVISION~, at whatever level and in
whatever order the divisions sit.  They are filled from the top.

Brief is the architect's brief: the conditions the design has to meet.
Every check is measured against it.

Brief is written by whoever asks for the output document -- you, handing
the file to an agent -- and is about the document: who reads it and what
it must keep to.  Subject, Message and Structure are about what the
document takes up, and they are kept apart by what each is checked
against.  A fact in Subject is checked against its source, a claim in
Message against the facts it stands on, and Structure against the
reader.  What the problem is taken to be is a claim, so it belongs in
Message, not Subject.

A division is an apex member like any other, and is broken down as any
member can be.  A new file is written in the basic form: the facts, what
they mean, what to do, told in that order.

| Member         | Pattern                                           | Written                                                               |
|----------------+---------------------------------------------------+-----------------------------------------------------------------------|
| Brief          | breakdown › reader-question-response-constraints  | an item for each role                                                 |
| Subject        | breakdown › parts                                 | a source, its facts as items under it                                 |
| Message        | breakdown › situation-interpretation-action       | Situation, Interpretation and Action                                  |
| Situation      | breakdown › parts                                 | a part, as an item, to be an include link to a source's truss         |
| Interpretation | breakdown › parts                                 | a claim, with ~TRUSS_LOGIC: reasons~ and a reason as an item          |
| Action         | breakdown › steps                                 | a step, as an item                                                    |
| Structure      | telling › Sky, Rain, Umbrella                     | ~[[truss-include:m1]]~, ~m2~, ~m3~: Situation, Interpretation, Action |

Structure's headings are include links alone, so each is the member it
includes there, and that member's words are the output document's
heading.  Situation is the sources the reader is shown first, each
whole: its parts include the trusses of the sources whose facts the
claims stand on, and no others, so the reader sees what each source says
before what is drawn from it, and a source added to Subject, however
poor, reaches the output document only once a claim stands on it.
/Sources in Situation/ lists what it shows amiss.  A new file is an
output document as it stands, each word of it to be written over, which
/Words to write/ lists until it is.  Action points to the claim it
follows from, once; a step takes a ~TRUSS_LOGIC~ of its own only for
reasons of its own.  For a document of another form, give Message and
Structure other patterns: /pattern/ on the division's line on the board
puts one on, and puts in a member for each role it lacks.  The facts
stay in Subject.  What each division, and each role of Brief's and
Message's breakdowns, is for, ~?~ on its line of the board says.

The members of the divisions are members like any other: they can have
grounds, be assumptions, be apex members of trusses of their own and be
included by Structure.  A book states its intended reader; a proposal
states the constraints it works within.  Such a statement is written once,
under the role it belongs to, and Structure includes it from there.  A
fact that cannot be shown -- a figure that is confidential -- is tagged
~:noexport:~ in Subject; a claim the output document tells that stands on
it is listed under /Hidden grounds/.

The work on an output document goes in three steps, one division each.

- /Find out/, in Subject.  Gather the facts, each with its grounds, one
  truss for each source: a member whose words are the link to the source
  as its apex member, the source's facts as its supporting members.
- /Make sense/, in Message.  Say what the facts mean here, and what is to
  be done, one statement each.  A claim's reasons are its supporting
  members, and stand on the facts they point to in their text; what is to
  be done is broken down into steps, which point to the claims they
  follow from.
- /Tell/, in Structure.  Its members are the headings of the output
  document; their text includes the trusses and members the reader is
  shown, from any division.

Where a member is written changes nothing of how it is checked or
written out.  The divisions keep what was found apart from what the
output document says of it.

** Patterns and roles

An apex member names patterns for its supporting members, of three
kinds, in ~#+attr_truss~ in its text; each of those says the role it
plays in each pattern before its words, then ~::~ (see [[*Writing
members]]).  Properties say the same, a heading's: the pattern's, and
the role's with ~_ROLE~ after it.

| In ~#+attr_truss~ | Property          | Role property          | Its supporting members are  | Patterns                                    |
|-------------------+-------------------+------------------------+-----------------------------+---------------------------------------------|
| ~:logic~          | ~TRUSS_LOGIC~     | ~TRUSS_LOGIC_ROLE~     | its reasons                 | reasons, deduction, induction               |
| ~:breakdown~      | ~TRUSS_BREAKDOWN~ | ~TRUSS_BREAKDOWN_ROLE~ | its breakdown: its parts    | steps, parts, 5W1H, 6W1H, pros and cons ... |
| ~:telling~        | ~TRUSS_TELLING~   | ~TRUSS_TELLING_ROLE~   | told in the pattern's order | PREP, SDS, SCQA, Sky, Rain, Umbrella        |

The three are apart.  A member has at most one of each, and a supporting
member plays a role in each its apex member has: a reason that is also a
pro, and told as PREP's reason, says ~reason~, ~pros~ and ~reason~ in
the three.  A member with members under it and no pattern is listed /No
relation/: nothing says what they are to it.  Every member takes all
three, and reads them alike: a division, a member of Message, a member
of Structure.

/Logic/ is the truss itself: what holds the apex member up.  The three
are told apart by taking one supporting member out.  Reasons each hold
it up alone: take one out and the rest still do, if less.  Each reason
is a deduction whose major premise goes without saying -- /half the
items repeat/, so /the review need not be weekly/, on the unsaid
premise that a meeting whose items repeat can meet less often -- and
where such logic is weak, it is weak there, in what goes without
saying.  A deduction's major and minor premise hold it up only
together: take one out and nothing follows, so both are written.  An
induction generalises two cases or more of one kind: fewer make it
weaker, as with reasons.  A premise that
needs proving is itself the apex member of a deduction, so a chain of
reasoning is a compound truss.  Each reason must have grounds; see
[[*Grounds]].

/Breakdown/ is what the apex member is made of.  Steps are in order, parts
in none; the other breakdowns name their parts -- pros and cons; past,
present and future; who does it, to whom, when, where, what, why and how
-- so that nothing is left out.  A part needs no grounds of its own: what
holds up the whole holds it up.  An output document is written for
someone, and what it asks done is mostly done by someone to someone, so
6W1H is the cut to reach for when nothing smaller does; 5W1H, without
/whom/, is there for what is done to no one.  A notice reads naturally cut
this way, with its steps inside its /how/:

#+begin_example
Check before every test

- Who: the driver's manager
- Whom: whoever drives in the test
- When: before the first run of the day
- How: as follows

  1. Meet the driver, face to face or by video call
  2. Read the checker
#+end_example

Steps and parts differ by whether order matters.  /Keep a record of each
check/, in parts: the name of whoever checked, the driver, the time, the
reading, what was said; in any order, nothing is lost.  /Check before
every test/, in steps: meet the driver, then read the checker; in another
order, it is another procedure.

/Telling/ is a framework of telling, which says nothing of what is told:
its places in order, each played by a supporting member.  PREP is a
point, a reason, an example and the point again; each is a member you
write, the point again too, in the words it is to be told in the second
time.

Everything is told in the order of the file: an apex member before its
supporting members, and those in the order they are written, the order
the reader meets them; the board shows it so.  A telling pattern changes
nothing of that order.  It asks for its places, and what the file has
below a member the pattern tells after it is marked =⚠= and listed /Out
of order/, to be moved in the file.

So a claim is told before its reasons: the pyramid, read top down.  A
story that keeps the conclusion for the end -- SCQA, Sky, Rain, Umbrella
-- is told by the members of Structure, the claim included in the last of
them; its reasons come after it there, as they are its supporting members.

| On the board                                  | Gives                                                        |
|-----------------------------------------------+--------------------------------------------------------------|
| logic › reasons                               | reasons that each hold it up alone                           |
| logic › deduction                             | a major and a minor premise, together                        |
| logic › induction                             | two cases or more, that it generalises                       |
| breakdown › steps                             | what to do, in order: a numbered list                        |
| breakdown › parts                             | what it is made of, in no order: a bulleted list             |
| breakdown › What, Why, How                    | what it is, why, and how                                     |
| breakdown › Pros and cons                     | what is for it, what is against it                           |
| breakdown › Short and long term               | what holds soon, what holds later                            |
| breakdown › Past, present, future             | what was, what is, what will be                              |
| breakdown › 5W1H                              | who, when, where, what, why, how                             |
| breakdown › 6W1H                              | who, whom, when, where, what, why, how                       |
| breakdown › Situation, Interpretation, Action | the facts as they are, what they mean, and what to do        |
| telling › PREP                                | point, reason, example, the point again                      |
| telling › SDS                                 | summary, details, the summary again                          |
| telling › SCQA                                | situation, complication, question, answer                    |
| telling › Sky, Rain, Umbrella                 | sky, rain, umbrella: what is seen, what it means, what to do |

Sky, Rain, Umbrella is fact, interpretation, action: the sky is clouding
over; it will rain, then; take an umbrella.  It is a way of thinking as
much as of telling, and it tells the umbrella last.

Patterns nest: the umbrella of one Sky, Rain, Umbrella can hold another,
and a deduction can stand where SCQA puts its answer.

/pattern/ on the board offers every pattern, of each kind, on any member,
and takes one of a kind off.  What the pattern asks for and is not there
is put in, a member for each role named for it and playing it, where the
pattern lists it, to be written over: a deduction's premises, a PREP's
reason and example, a 6W1H's seven.  On a member of Structure, a telling
pattern first takes the members there into its places by their
~TRUSS_TELLING_ROLE~, and puts them in its order in the file.

Every pattern is written in ~org-truss-patterns~ in one form: its kind,
its roles in order, and, for a breakdown, the list it is written out as.
Each role can say how it is asked for:

| Flag          | The role                                                               |
|---------------+------------------------------------------------------------------------|
| ~:at-least N~ | is asked of N members or more: induction's cases, two                  |
| ~:any~        | takes what plays no role: SDS's details                                |
| ~:label~      | opens each part playing it with its name when written out: Pros:, Who: |

~org-truss-patterns~ takes patterns of your own in the same form -- a
breakdown from ~org-truss-roles~, a framework of telling -- and
~org-truss-roles~ the roles they name.

** Writing members

A member is a heading, or an item of a list marked ~#+attr_truss~ in a
member's text, as you choose.  What a member is -- an apex member, an
assumption -- does not decide it, and the output document is written by
what each truss is, not by how it is written (see [[*The output
document]]): an item can become a heading, or a heading an item, and
nothing else has to.  Org sets two limits:

- A heading has no text after the headings under it: a member whose text
  goes on after or between the trusses in it holds them as items, in
  nested lists.
- Under one member, the items come before the headings.

Make a heading of a member pointed to from several places, to be found
easily, and keep in one heading a truss checked at once -- the facts of
one source, a claim and its reasons.

An item takes tags as a heading does, at the end of its first line,
~- It is quick :assumption:~, read by
[[https://github.com/yoshzucker/org-item-tags][org-item-tags]]; with
~org-item-tags-mode~ on, ~C-c C-q~ there sets them, and ~C-c -~ and ~C-c
*~ keep them between a heading and an item.

Org's ~C-c *~ makes items headings, and ~C-c -~ headings items.  In a
truss file they keep what makes each a member as it is written: the role
it plays, or its value, before ~::~; the patterns, ~:by~ and ~:as~ of
its truss, in ~#+attr_truss~; its ID, ~<<m7>>~, with its words.  A role
in a ~_ROLE~ property goes before ~::~, and the patterns in properties
into ~#+attr_truss~, when a heading is made an item, which has no
properties; a ~CUSTOM_ID~ is made ~<<m7>>~.  Where Org would put a
member under another -- the items after the one made a heading, a
heading made an item in the text of the heading before it -- they do
nothing, and say so: make the rest headings too, or start from the
first heading.

A member's patterns go in ~#+attr_truss~ in its text, and the role it
plays before its words, then ~::~ -- a heading and an item alike, so
what a member is shows where it is written:

#+begin_src org
,** We move to fortnightly reviews
We would meet half as often.
,#+attr_truss: :logic reasons :breakdown pros-cons
- pros :: <<m21>>Less time in meetings
  An hour a fortnight back, by [[m2]].
- cons :: Items wait longer
  ,#+attr_truss: :breakdown steps
  1. Ask the leads
  2. Ask the team
,*** pros :: Fewer items carried over
#+end_src

- ~#+attr_truss~ right before a list marks it: its items are the
  member's supporting members, and come before the headings under it.
  One that marks no list -- a line of its own, before the headings
  under the member -- names the member's patterns all the same.
  ~#+attr_truss:~ naming none marks the items alone.
- The properties say the same, a heading's: ~TRUSS_LOGIC~ and the rest
  for its patterns, and the property of the same name with ~_ROLE~ after
  it for its role.  What a property names is read before ~#+attr_truss~
  and ~::~, which take the kinds it leaves out; the board and /new/
  write where the member writes it already, and else ~#+attr_truss~ and
  ~::~.  A heading playing two roles names one before ~::~ and the
  other in its property.
- The term before ~::~ is the role a member plays, by its English name,
  as in ~TRUSS_BREAKDOWN_ROLE~, of a pattern the member above has; a term
  that names no role is part of its words.
- A pattern of one role -- ~reasons~, ~steps~, ~parts~ -- has no role
  written: every member under it plays it, but one that names another
  role of its kind.  So a heading under it that is an include link
  alone, or a fact tagged ~:assumption:~, needs nothing written, and the
  board writes nothing.
- An item's first line is its words, as a heading's are; the lines under
  it are its text, a comment left out; a list marked so inside it holds
  its supporting members.  A list not marked stays text, the include links
  ~- [[truss-include:m7]]~ of a member of Structure among it.
- A target in its first line, ~<<m21>>~, is its ID, as one in a
  heading's words is the heading's: ~[[m21]]~ points to it, and
  ~[[truss-include:m21]]~ includes it.  /new/ gives a member it writes
  one, before its words.
- ~:as~ in ~#+attr_truss~, ~headings~ or ~list~ (~TRUSS_AS~ as a
  property), says how the output document writes the supporting members
  of that one truss, where what it is would write them the other way.
- ~:by~ in ~#+attr_truss~, after the breakdown it cuts (~TRUSS_BY~ as a
  property), names an axis (see [[*Axes]]).

Every division reads items so, Brief and Structure among them:

#+begin_src org
,* Structure
:PROPERTIES:
:TRUSS_DIVISION: structure
:END:
,#+attr_truss: :telling sky-rain-umbrella
- sky :: [[truss-include:m2]]
- rain :: Why change
- umbrella :: [[truss-include:m1]]
#+end_src

On the board, /edit/ on an item takes out the heading whose text holds
it, at the item; /pattern/ on an item names the pattern in the
~#+attr_truss~ right in it, and puts in its list an item for each role
the pattern asks for; /roles/ writes its role before ~::~, one an item
can name; ~m~ takes a source for it.  The other commands that change a
heading say so on an item instead, which is written by hand there.

** Grounds

In a ~TRUSS_LOGIC~ truss, each supporting member has grounds.  Grounds
are, in its text:

| a pointing link or an include link | to a member, ~[[m3]]~, ~[[truss-include:m3]]~                   |
| a link to a source                 | a ~moor:~, ~file:~ or URL link                                  |
| a quote                            | ~#+begin_quote~, the source's own words                         |

These supporting members need none:

- the apex member of a ~TRUSS_LOGIC~ truss: its supporting members are
  its grounds;
- a member tagged ~:assumption:~, taken as given: the user decided so,
  and only the user tags it;
- a member tagged ~:open:~, until it is settled (see [[*Scope]]).

Whether a member must have grounds comes from its role alone: not from
the division it is written in, nor from whether anything includes it.

A member a member links to as grounds is a reason it stands on, by a
link, as a reason written under it would be (see [[*Patterns and
roles]]): a deduction whose major premise goes without saying, holding
it up alone.  Two that hold it up only together are no grounds but a
deduction, written as a truss with its major premise.  Sources and
quotes are where the reasons end: what was found, not argued.  In the
output document:

| Ground                             | In the output document                        |
|------------------------------------+-----------------------------------------------|
| a reason by an include link        | the member, there                             |
| a reason by a pointing link        | its words, in the sentence; the member is not |
| a source                           | a link to where it came from                  |
| a quote, ~#+begin_quote~           | the quotation                                 |

Grounds are written in the text the reader is shown, and cite there: a
pointing link reads as m7's words, so it is written into a sentence; a
~moor:~ link is a link to where its source came from (see [[*The output
document]]).  So a source is written once, where it is cited.  A link
on a comment line, ~# [[m3]]~, or in a comment block is no ground: what
a member stands on is said where the reader sees it.

Words naming what has no file -- /team agreement/, /what was said in the
hallway/ -- are no grounds: nothing in the file can be gone back to.
What a person said is a source once it is written down: the answers as
they were given, in a note titled by the date and the person, taken
into ~sources/~ and quoted.  What nobody said and the user takes as
given is tagged ~:assumption:~.

An include link in a reason is grounds as well as what it includes: a
reason is asked why it holds, and one that included m7 and did not stand
on it would put beside itself what has nothing to do with it.  A member
whose words are an include link alone, ~*** [[truss-include:m7]]~, is m7
itself there: a fact that needs no words of yours to be the reason is not
said again by a member of its own.  In a member that is no reason -- a
part of a breakdown, a member of Structure -- the link only includes.

A member pointed to as grounds has grounds too, or needs none:

| Pointed to          | Holds when                                                               |
|---------------------+--------------------------------------------------------------------------|
| a member, ~[[m3]]~  | it has grounds, a ~TRUSS_LOGIC~, or the tag ~:assumption:~               |
| a source, ~moor:~   | the truss file's ~sources/~ holds it                                     |
| a file, ~file:~     | it is there                                                              |
| a URL               | not checked: nothing in the file can tell                                |

It is asked one step: what a member pointed to points to in turn is asked
of that member, where it is written.  Whether a source says what it is
cited for is past what the file's structure can tell.

The line between a fact and an assumption is whether you can say where it
came from.

** Claims

Subject is written up from the sources; Message is written down from its
end.  What Brief's response asks for comes first, and under it only the
claims the reader needs to be convinced of it.  How many claims there are
is then set by what the document has to say, not by how many facts were
found.

Two kinds of claim are not made: one between a claim and the facts that,
pointed to straight, convince of it; and one that says a fact or another
claim again.  The fact or claim is pointed to or included instead, not
written again in other words.

A claim is worth setting apart, to be pointed to or included, when it
saves more than it costs.  Standing on n grounds and used by k members,
it is n + k links where pointing to the facts straight would be k × n.
So a claim is set apart when two or more members use it, by a pointing
or an include link, and it stands on two or more grounds.  One used in
one place is a reason, written under the member using it, a heading or
an item.

Two checks count these (see [[*What is left to do]]).  /Set apart/ asks
it of each claim set apart in Message, a heading or an item: not one
right under the division, where its breakdown is told; not one in what
plays /action/, a step being no claim; not a reason written under the
member it holds up, which is where it is used already.  A member uses it
by pointing to it, standing on it or including it, or by including a
member it is under, which brings it into the output document --
Structure including Interpretation whole, say.  Its grounds are the
members and sources it links to, its quotes, and its reasons.  /Said
again/ finds members of Message that stand on the same members, two or
more, as another does.  A claim that only reads one fact again is past
what the file can tell from one read on its own: one fact can bear a
claim of its own, as a rule read for this case does.

Grounds are pointed to from the highest member they hold up.  When every
supporting member of an apex member stands on the same member -- each
step of Action on the claim it follows from -- that member holds up the
apex member, not each of them, and the apex member stands on it instead,
once.  /Grounds set low/ lists the apex member.

A claim is as wide as its grounds hold up, and no wider.  Wider, it says
what they do not -- /every team/ from one team's minutes -- or says
nothing at all; narrower, it is the fact said again.

The words of an apex member and its supporting members alone -- a
heading, an item's first line -- show its pattern holds: a claim and the
words of its reasons, read without their text, are enough to see the
reasons bear it.  Trusting that each is held
up by what is under it, a reader follows the document by its words, and
each claim is checked on its own, against what is right under it.  Words
fit one line, about 60 columns.

** Axes

What is found is laid out so that nothing is left out and nothing
overlaps by cutting a breakdown by an axis: ~:by~ after the breakdown in
~#+attr_truss~, or ~TRUSS_BY~ on a heading.  Its supporting members are
then all there is, each by its /value/: the term before ~::~, an item's
or a heading's, or else the member's words.

#+begin_src org
,** Expenses
Amounts are cut by the rules, art. 3 [[moor:6f1c...::3][art. 3]].
,#+attr_truss: :breakdown parts :by Amounts
- Under 100k :: The section head approves [[m21]]
- 100k or more :: The department head approves [[m22]]
#+end_src

That the values are all there is, is a claim, and whether they are can
be told from what they mean alone: /under 200k/ and /under 100k/ are
written alike and leave a gap.  So the file asks where it can be told:

- The apex member has grounds in its own text that the values are all,
  in a paragraph that names the axis by the word ~:by~ gives it --
  /Whole without grounds/ and /Axis not named/.  Grounds are written
  once, at the highest member they hold up: one quote there holds up
  every value it says, and a value another source says points to its
  fact in Subject.  Not known yet, it is ~:open:~.
- A value with nothing after it is listed, /Missing cells/: what is
  there is written, /none/ with its grounds when there is none, or it is
  ~:open:~.  So what is not there and what is not known yet are told
  apart.
- Items whose terms, two or more, name no role read as values of an axis
  no ~:by~ names: /Values without :by/.

A value under an axis is no claim set apart: it is placed where it is
used, as a reason under the member it holds up is.

Two axes cut a member as a table does when every supporting member is
cut again by one axis: rows by the one, columns by the other.

#+begin_src org
,** Expenses
Amounts are cut by the rules, art. 3 [[moor:6f1c...::3][art. 3]]; each
stage by the FAQ [[moor:a90b...::2][Q2]].
,#+attr_truss: :breakdown parts :by Amounts
- Under 100k ::
  ,#+attr_truss: :breakdown parts :by stage
  - approval :: The section head [[m21]]
  - payment :: Month end [[m23]]
- 100k or more ::
  ,#+attr_truss: :breakdown parts :by stage
  - approval :: The department head [[m22]]
  - payment :: :open:
#+end_src

The grounds that both axes are whole are the apex member's, which names
both; the rows need none of their own.  A column a row has no cell in is
listed under /Missing cells/, and so is a cell whose words are its value
and nothing more.  The board names each member by its value, and its
pattern by its axis, /breakdown › parts by Amounts/.  The output document
writes such a member as a table (see [[*The output document]]); one whose
cells hold more is told as a tree, which holds every table and more.

** Scope

What Brief asks for sets what is needed: the sources and facts reached
from the claims of Message, following what they stand on (see
[[*Grounds]]), are needed; what Situation, or Structure, includes of
Subject only shows it.  So what is to be looked into, and what not, is
told by what the document has to say, and the work stops where nothing
needed is left open:

1. Whether a source or a fact is needed is set by whether the response
   Brief asks for needs it to be reached: those reached from the claims
   of Message, following what they stand on, are needed.
2. ~:open:~ tags a question or a claim not settled yet; its text says
   where to look, or that it is unknown.
3. From a source not ~:aside:~, the other sources it refers to are
   followed.  Each one followed is taken, or written as one line tagged
   ~:aside:~, so it is not looked into again.
4. A fact is written only when a claim, or an ~:open:~ that is needed,
   stands on it.
5. A source ~:aside:~ has no supporting members; its text and quote may
   be short.  The other sources it refers to are not followed.
6. An ~:open:~ that is unknown is asked of the user.
7. Only the user tags ~:assumption:~: what an agent would fill in from
   what it knows stays ~:open:~, for the user to take as given or not.

A member ~:open:~ needs no grounds meanwhile, and is listed: /Open/ when
something needed stands on it, or it is in Message; /Open, not needed/
when nothing does, not to be looked into.  /Open in the output/ finds one
the output document tells, /Settled/ one that has grounds and keeps the
tag.  /Unused/ finds a fact nothing needed stands on, and /Aside with
members/ a source set aside that holds members.  A source set aside is
told like any other when Structure includes it.

** One source at a time

Write a truss to be checked against one source; the check sees to it.

- A parts truss: the links to sources in its end members' text point into
  one source.  An apex member among its supporting members is held to
  this itself, and may point into another -- a form's fields under the
  form, beside the law under the law.
- A ~TRUSS_LOGIC~ truss, in any division: the links to sources in the
  text of its apex member and of every member under it point into one
  source.

A source taken by org-moor is one wherever in it its links point and
whatever words they give it, ~[[moor:ID::14]]~ and ~[[moor:ID::200][field
B]]~ alike; a file is one, a URL is one.  Pointing links are no sources.

A truss pointing into one source names it once, in its apex member:
its words are the link with the source's title, ~[[moor:ID][Manual]]~.
They name the source, not what is drawn from it: that is a claim, and
its place is Message.  So a reader sees where one source's facts begin,
and that all under it are of that source.  Under it, each link is named
by its place alone, ~[[moor:ID::223][l. 223]]~, ~[[moor:ID::12][p.
12]]~ -- in an item, at the end of its first line, not on a line of its
own, so the output document gives the place at the end of the fact, not
as a paragraph after it:

#+begin_example
,** [[moor:6f1c...][Approval manual 2026]]
,#+attr_truss:
- <<m21>>Approval goes to the department head first [[moor:6f1c...::12][p. 12]]
- <<m22>>Finance approves last [[moor:6f1c...::14][p. 14]]
#+end_example

The link goes to the same source either way; only its words
change, so the file and the output document say which source once,
in the heading the facts of it begin under, and where in it beside each
fact.  With
org-moor, what it writes in ~truss.org~ -- a place noted beside the
source, ~C-c C-l~, what an agent the heading is handed to is told to
write -- is named so: a link to a place by the place, one to the source
by its title.  A fact included alone, its apex member left where it is,
is not left without its source: see [[*The output document]].

To bring facts of different sources together, point to the members that
hold them, not to the sources: the work of Message.  So Subject reads as
its sources do, each truss checked against one, and the mesh of what
stands on what is woven in the pointing links alone, where each reason
shows what it reads.

* The file

There is one ~truss.org~ per output document, in a directory of its own.
~M-x org-truss-init~ sets the directory up; run on one set up before, it
adds what is missing and leaves what is there.

| ~truss.org~ | the file; the rest is written from it or for it                        |
| ~sources/~  | sources referred to: with org-moor, a directory each, its file and record |
| ~notes/~    | what is ours and no source: memos, slides of our own, minutes          |
| ~attach/~   | what ~org-attach~ (~C-c C-a~) attaches to a heading: a picture, a file |
| ~out/~      | the output document, written by ~x~ on the board or ~M-x org-truss-export~ |

So the directory can be moved, or handed over, whole.  With org-moor, a
source taken from a truss file goes in its ~sources/~: a directory named by
the source's id, holding its replica and its record -- a title, where it came
from, how and when.  A member cites it with a ~moor:~ link, ~[[moor:ID::12][p. 12]]~
for a page or a line, the source named once above it (see [[*One source
at a time]]), in its text, beside the words it quotes or
on a line of its own; either gives it grounds.  The first line of
~truss.org~ sets ~org-attach-id-dir~ to ~attach/~, so what ~org-attach~ puts
on its headings is kept there, not where attachments go elsewhere, each
heading's in a directory named by its ~ID~; it is a file variable Org
declares safe, so it holds whether org-truss is loaded or not.  The board
and the output document read a link to an attachment,
~[[attachment:NAME]]~, as a link to its file.

~org-truss-project-file~, when it names one, is an empty file written there
too, that marks the directory as a project: ~".project"~, say, with
~project-vc-extra-root-markers~ naming it.  Then the directory is a
project even outside a repository, and what starts at a project's root --
a coding agent among them -- starts beside ~truss.org~ and its sources.
Inside a repository it makes the directory a project apart from the rest.

** The guide

A ~:GUIDE:~ drawer at the head of ~truss.org~, before the first heading,
holds the rules of the file, the same for whoever edits it, by hand, on
the board, or as a language model working in the file: the words above,
the four divisions, how members and trusses are written, grounds,
claims, sources, what is in the output document, what goes in the
directories beside it, and the command that checks the file.  Org folds
it as it folds any drawer, out of the way of the divisions, and ~TAB~ on
it opens it to be read.  Its example is in an example block, and its
IDs, ~<<m21>>~ among them, are no member's: IDs are counted from the
first heading.

What each division, and each role of Brief's and Message's breakdowns,
is for is not written in the file: ~?~ on the board says it in the echo
area, on the line of the division, of the member playing the role, or of
the role missing; on any other member, ~?~ says its patterns and the
roles it plays.  ~org-truss-batch-guide~ prints the guide and all of
these, for an agent (see [[*Batch]]).  The board's keys are at its foot,
and what each check finds is said where it is reported.  The words of a
new file are English whatever ~org-truss-language~ says: they name the
divisions and the roles, to be written over; those Structure includes
reach the reader until they are, and /Words to write/ lists them.

The guide learns, and a file keeps the wording it was written with.
~M-x org-truss-refresh-guides~ puts the current guide back in its
drawer, in place of the guide before it -- a drawer, or the comments it
was once written in -- and takes away the ~:GUIDE:~ drawers once written
under the divisions and the members playing their roles.  One of your
own, of a role nothing is said of or of any other member, stays, and so
does anything else you wrote.

** Members assert; Structure tells

A member's words are the sentence it asserts, and what the checks read.
Links point to it by its ID, not its words, so they can be reworded at any
time.  It can be wrong and can stand on others, so write it to read on its
own, pulled out of the output document -- no "the following", no "above",
no "first".  The order it is told in is Structure's, and words that lean
on that order stop being true when Structure changes.  What a member
asserts is tied to the reader's question, in Brief: ask another question
and the top claim changes, while what it stood on stays.  It is not tied
to how it is told.

Structure asserts nothing.  It chooses what the reader sees and in what
order, and writes only what guides them -- what is true of the output
document rather than of the world, so it needs no grounds:

- a member of Structure's words, a heading of the output document;
- its text, read under that heading before the members it includes.
  Structure's own text opens the output document;
- the include links, where they stand -- in its items, or in its text,
  between the words that lead from one to the next.

[[truss-include:m13]]
#+end_src

The joins between members are seldom Structure's to write either: a
member's patterns say what its supporting members are to it -- steps
numbered, a part labelled with its role -- and the output document is
written so.  Whatever could be wrong is a member, where the checks reach
it.

A member is written out as its words, wherever it is included, and its
text follows them: what it says more to the reader.  To say it to the
reader otherwise, rewrite its words -- what it asserts is what the reader
is told.  What is for you alone -- why you believe it, who said it, what
cannot be said -- goes in a comment, as Org writes one, which stays in
the file:

A member tagged ~:noexport:~ stays in the file whole, with what is under
it: evidence you keep for yourself, a note on what to check.  An output
document generated from the file can be generated again as often as you
change it, so the file stays the place where the thinking happens, and the
output document is never a copy that has to be kept in step by hand.

** What the outline means

Within the divisions, the outline carries meaning in these places only:

- Under an apex member, its supporting members play its roles, and the
  order they are written in is the order a telling pattern tells them in,
  and steps are done in.
- Under Brief, Subject and Message, the order of the members means
  nothing besides; the board and the output document follow the links.
- Under Structure, the outline is the output document's: its headings, in
  order.

So members can be reordered and reworded freely; putting one under
another, though, makes it a supporting member of the other, and a member
moved under a member of Structure would be read as a heading of the
output document.  The board does not depend on where in the file a
member is written -- only on what it is under and what links to it.

** Two links to a member

A member is linked to in one of two ways, and the kind of link alone says
which: not where it is written, nor whether it is a list item, nor what
kind of member it points to.

| Link                   | What it does                                                                           |
|------------------------+----------------------------------------------------------------------------------------|
| ~[[m7]]~               | a pointing link: points to m7 as grounds, in a member's text                           |
| ~[[truss-include:m7]]~ | an include link: includes m7 there, with what is under it, in the output document      |

An include link can stand in any member -- a member of Structure, or one
that brings another along -- on a line of its own, as a list item, or in a
sentence; or as the words of a member, ~*** [[truss-include:m7]]~, which
is then m7 itself.  Where it stands says how m7 is written out.  On a
heading line, it is a heading of the output document: its words, then
what is under it, under headings a level down.  In text, it is its words
in the sentence, and the rest -- its text, then what is under it --
follows the paragraph, or goes inside the list item, as a list.  Its
description, ~[[truss-include:m7][words]]~, is its words there.  Two
places that include the same member include it twice: that is yours to
want or not.  A pointing link reads as its description, or m7's words; in
a comment it is not written out.  What a member brings with it is
included inside it, and so on down; an include link that would include
what includes it back, without end, is reported under /Broken links/, and
the output document says so where it stops.

** Pointing to a member

Both links point to a member by its ID: ~m7~ is the heading or the item
with ~<<m7>>~ in its words, before them.  The ID goes with the words,
so a heading made an item, or an item a heading, keeps it, and nothing
pointing to it changes.  A heading with
~:CUSTOM_ID: m7~ is m7 as well, and a link may be written ~[[#m7]]~: in a
truss file, with org-truss loaded, ~C-c C-o~ follows ~[[m7]]~, ~[[#m7]]~
and ~[[truss-include:m7]]~ to m7 however its ID is written, where Org
alone takes ~[[#m7]]~ to a ~CUSTOM_ID~ and ~[[m7]]~ to a ~<<m7>>~.  An ID
stays within the file: unlike ~:ID:~, it is not entered in
~org-id-locations~, nor made a node by org-roam.

A member's words are what it asserts, and they get reworded as the
argument and the output document take shape.  Were links to name words,
each rewording would break what pointed to it; pointing by ID, a member
can be reworded anywhere -- in the file by hand, or by a model editing
the file -- and nothing breaks.

A member is given an ID once something points to it: written by hand,
~<<m7>>~ before its words, or by /new/ writing it in Structure.  An ID
is ~m~ and the next number free in the file, counted from the first
heading.  Two members with one ID, and a link that points to no member,
are reported as /Broken links/, at each in the division it is in.

A link written by words, ~[[*words]]~ or ~[[truss-include:*words]]~ --
with Org's completion, say -- names no ID and shows as broken.

* The board

~M-x org-truss-board~ draws the nearest ~truss.org~: under its title,
Brief, Subject, Message and Structure, in the order the work is done,
each followed by what is left to do there.

The board is where a truss file is worked from, as the agenda is for Org
files.

A heading of any other Org file can be drawn on a board of its own: in a
file that is no truss file, ~M-x org-truss-board~ draws the nearest
apex member at or above point -- or, when no truss file is near, the
heading at point -- as a truss file's members are drawn, under a line
/Heading/.  Its patterns, its supporting members by the roles they play,
and the roles still missing are all there, without Brief, Subject or
Structure.  /pattern/ on it puts a pattern on it, and a member in for each
role, to be written over -- and in the file itself, in a truss file or any
other, ~M-x org-truss-apply-pattern~ does what /pattern/ does, on the
heading at point; written over with the statement that plays it, a role
still shows before its words what it is -- /Who:/, /When:/ -- so the words
need not say it.  An agent asked about it with org-dock is told what its
patterns ask, and how to check its copy; see [[*Batch][Batch]].

It can be called from anywhere: when no ~truss.org~ is near the current
buffer, or with a prefix argument, it asks for one as ~find-file~ asks for
a file -- the file, its directory, or anything below it -- and offers to
start one in a directory that has none, making the directory if it is
new.  The file's own buffer can be closed whenever it is not wanted: the
board visits it again before its next command.  ~C-x C-s~, or whatever
saves a buffer, saves it from the board, and the title line says
/unsaved/ until then.

** Two columns

Each line has two columns.  On the left is what the board says the line
is: the role a member plays in the patterns above it -- /member/ for one
that plays none -- and the tree that joins them.  After the role come,
in brackets, what wants seeing to: =[no role]= for a supporting member
that plays no role of its apex member's patterns, =[no pattern]= for one
that plays a role the member above has no pattern for, =[assumed]= for
an assumption, =[open]= and =[aside]= for one tagged ~:open:~ or
~:aside:~, =[noexport]= for one tagged ~:noexport:~, =[no grounds]= for
a reason that must have grounds and has none.  Dots lead from the left
to the words, and the mouse on them names the member by its ID as the
file names it: =<<m9>>= where it is written, and =[[m9]]= where an
include link includes it; a member under one a link brings, as where it
is written.  From one column the same on every line come the file's own
words -- members' words, the title -- and links read as the reader reads
them: a member whose words are an include link alone reads as the words
of the member it includes, after what that member is where it is
written, its division and the roles down to it,
=↪Message›Interpretation›Part=; see [[*Marks]].  A heading is the
reader's words, and its text is what the reader is told but its
comments, so the words are what the output document says: a member it
writes as an item of a list opens with its bullet, =- =, or its number,
=1. =, and the role it plays when the pattern labels it; one it writes
as a heading -- a compound truss's supporting member written as a
heading, or one under a pattern that lists nothing -- opens with no
bullet, its number and its role alone.  Once an item, all under it is a
list, as in the output document; a member an include link in a member's
text includes is an item.  A heading's words are in the face Org gives a
heading of its level, so they look as they do in the file; the board
colours them itself, so it does not matter whether the file has been
shown yet.  Over it they are in the face ~org-truss-outside~, slanted by
default, while the output document does not include the member.  A
division's line says its name, /Brief/, /Structure/, and then its
heading's words, which never reach the reader; the mouse on it says what
is done there.  The left is as wide as it needs; the words take the rest
of the window, and are drawn again when it is resized.  Words too long
for it are cut short at the window's edge, the whole of them in the
tooltip, unless the line is drawn whole; see [[*Reading lines whole]].
What a member holds starts two columns right of its word: the sources it
stands on, the members its links include.  Its supporting members branch
off from the column of its word.  The line of the tree starts right
under the line naming its patterns and runs down past whatever comes
before the first branch -- the sources it stands on or the members its
links include, and drawn whole its text -- so each member is held by it
as far down as it goes.  The tree of the members outside Structure is
drawn in the face ~org-truss-branch~, faint by default, so where it
meets Structure's tree the two read apart.

The two columns say the same in every division.  The left is where a
line stands in the patterns; the words, what is asserted and how the
reader is told it, so whether the logic holds -- or, in Structure,
whether the story does -- is read down it, and, drawn whole, whether it
reads as prose.  A member's line is the same where it is written and
where a link includes it.

** Marks

There are two kinds of link.  A pointing link is written by the member
that stands on it, ~[[m12]]~, in its text: logic, never written out but
as words.  An include link, ~[[truss-include:m12]]~, is written by the
member that includes it, a member of Structure or another: what the
reader is shown, and where.  A member is drawn where it is written, and
its line says little of its links:

| Mark                           | Where                                    | Says                                                                |
|--------------------------------+------------------------------------------+---------------------------------------------------------------------|
| =⏚m7=                          | after a member's words                   | it stands on m7, which no member is, or which has no grounds itself |
| =↪Message›Interpretation›Part= | before the words, which are a link alone | the member they link to is a part of Message's interpretation       |

What a member stands on is in its text, drawn whole as the reader reads
it: a pointing link as the words of the member it points to, in the face
of a ground; a link to a source as its words, in the face of a source,
or of what wants doing when it points to nothing; a quotation as a
paragraph of its own in quotation marks, after =✓= when its words were
found in its source, =✗= when not, =?= when the source cannot be read.
The mouse on a link says where it goes, and ~RET~ or ~C-c C-o~ on it
follows it: one to a member goes to the member's line on the board,
unfolding what hides it; one to a source opens it as the same key on it
in the file does, from where it is written there; ~m o~ on a link to a
source, or on a quotation, opens that source.  A link on a comment line is drawn as it
is written, dimmed with the comment, and is no ground.  With point on a
line, the lines linked to it light up, one step either way: where each
member it stands on is drawn, and each line standing on it or including
it.  /same/ goes to them in turn.  An include link written besides a
member's words has a line of its own under the member: =• included=, the
mouse on its dots naming the member it includes by its ID, =[[m12]]=.  A
member whose words are an include link alone is that member, and has no
such line; where it is written is said just before its words, its
division and the members above it -- how near to its sources what it
stands on is.  ~org-truss-board-marks~ sets the marks of a link, and
~org-truss-board-where-marks~ those before the words.  A role a member's
pattern asks for and it lacks -- /Minor premise —/ -- follows what it
holds, with the pattern that asks when the member has more than one.
/new/ on it writes a member playing it.

The other marks of the board are not links:

In Structure a member an include link includes is one line, as written;
opened there, as included (/order/), it brings with it what the output
document includes -- what is under it -- beside what it stands on,
sources and members, and its gaps, so the output document can be read
down Structure.

Each division is followed by what is left to do in it, check by check --
/Broken links/, /No grounds/, /Weak grounds/, /Hidden grounds/, /Quotes
not found/, /Grounds set low/, /Mixed sources/, /Sources in Situation/,
/Said again/, /Set apart/, /Missing roles/, /No role/, /No pattern/, /No
relation/, /Headings in a list/, /Out of order/, /Words to write/ (see
[[*What is left to do]]) -- each thing listed in the division it is
found in, and ~RET~ on it goes there.  The mouse on the name of a check
says what it finds.

The patterns a member names go on the line just below it, in parentheses,
where its supporting members branch off.  A step or a part opens with
the number, the bullet or the label the reader will see it with, and a
reason with the label of the role it plays in a breakdown.  A member
marked =⚠= comes below one the pattern tells after it; the output
document follows the order of the file, so the order is put right there.
The mark's tooltip, or ~C-h .~ on the line, says which.

Brief is the reader's only through the title.  Under the title come Brief, then
Subject, each drawn as the members are: its line, its patterns, and its
supporting members, each named by the role it plays, so what Structure has
to meet stays in view.  A role the breakdown asks for and none plays --
/Constraints —/ -- follows them, and /new/ on it writes a member playing
it.  A member that plays none of the breakdown's roles is marked
=[no role]=, and /roles/ gives it one.

** Reading lines whole

A line is drawn on one line, cut short at the window's edge, or whole.
Drawn whole, a member's words are broken to fit the window instead of cut
short, since the line is now read rather than scanned, and its text
follows them: what the reader is told, then its comments, which stay in
the file, after the =#= they are written with and dimmed.  The words
leave room beside their first line for a member it cannot stand on,
=⏚m7=.  The line naming its patterns stays right under its line, on the
left of what follows it; when it is too wide for the left it takes the
line after the member's words, and the text starts below it.  ~TAB~
draws a member whole as it unfolds it, as Org shows a heading's text as
it shows what is under it; see [[*Commands]].  With the members opened
where included, the board drawn whole is the output document, near
enough, beside the tree and the comments it was built from:

A picture linked on a line of its own -- an attachment, or a file by a

where Emacs shows no pictures, a link to a file reads as the file's name.

The board's words are English whatever ~org-truss-language~ says, so in a
file written in another language the two sides read apart at a glance.
What ~?~ says of a division or a role is in ~org-truss-language~, as the

** Commands

The board is read-only.  Its commands change the truss file and draw the
board again.  The writing itself happens in the file: ~RET~,
/visit-other-window/ and /show/ open it where the line points, as RET,
TAB and SPC do in the agenda, and /edit/ takes just that heading out, by
org-dock, into a copy of
its own beside the board, with what is under it and the rest of the file
out of the way.  The headings under it are folded to their lines, and its
own text is shown with its blocks open -- a comment block, its quotation
-- even where ~org-hide-block-startup~ folds blocks, since they are part
of what it says.  While it is out the heading cannot change in the file.
As in a capture buffer, ~C-c C-c~ there writes it back, saves the file and
closes the copy, and ~C-c C-k~ lets the copy go, the heading as it was;
its header line says so.  ~C-c C-c~ is taken for this, so a source block
in a member's text is run with ~C-c C-v e~ instead.  An agent can be asked
to work on the copy, and on nothing else; see org-dock.  Back on the board
after the file has changed, it draws again, and before each command it
draws again first if the file's text has changed, so the command acts on
the file as it is.  Only the text counts: fontifying the file, which
happens whenever it is shown, changes nothing the board holds.  An edit
made while a command is asking something makes the command stop and draw
again rather than act on positions that have moved.

The board's commands fall into four groups, by what they work on.
/Write/ works on the members themselves, in the file.  /Shape/ works on
the patterns of a member and the roles it plays.  /See/ moves about the
board and the output document.  Each is named here by what follows
~org-truss-board-~ in its name -- /pattern/ is ~org-truss-board-pattern~.
Few have a key of their own: those that move through the board and read
it, ~m~ for a source, ~x~ for the output document, ~?~ for what a line is
for.  The rest are called by name, ~M-x org-truss-board-pattern~, or
bound where you want them, in ~org-truss-board-mode-map~.  The foot of
the board lists those with a key, in the same three lines.  Writing,
moving, rewording and deleting members, include links and grounds is
done in the file, by hand or with Org's own commands.

/same/ goes round the lines linked to a member, one step either way.
On a line including it, =[[m9]]=, or showing it under a member a link
includes, it goes to where it is drawn in full, unfolding what hides it:
where it is written, =<<m9>>=, or, opened as included, the first line the
chain brings it to.  There, it goes to the first line linked to it --
where a member it stands on is drawn in full, a line standing on it or
including it -- and pressed again, to the next, and round, saying which
of how many it is.  The line at point is lit, and so are the other
lines naming the member on it -- where it is written, where it is
included -- and the lines
linked to it, in the face ~org-truss-same~; set
~org-truss-board-highlight~ to nil for neither.

~TAB~ cycles a line as it cycles a heading in Org, which shows a
heading's text as it shows what is under it.  A folded line opens to its
words whole and its text, with what is right under it, each of those
folded; again, everything under it is shown so too; again, it folds into
its line, which then says how many it hides.  Under a member, that is
its supporting members and what its include links include.  On a line
open on one line, as the board starts, ~TAB~ shows everything under it
whole first.  On a member with nothing under it, ~TAB~ draws it whole,
or on one line again; on a line a member brings below it -- its text, a
source -- the member cycles.  ~C-u TAB~, or ~S-TAB~,
cycles the whole board in three steps, as in Org: overview, every line
folded; contents, every line open on one line; and everything, every
line whole.  /fold/ folds one line or unfolds it, without the cycle.  The
board starts as an Org file does in overview: every line with something
under it folded, each line on one line.  ~org-truss-board-fold-limit~, 0
unless set, is how many a member may hold and still start open; nil
starts the board open.  A member an include link includes starts folded
where it is not opened, as /order/ says, since it is drawn in full where
it is.

A link is drawn as what it does.  An include link includes, and the
member it includes is drawn below as =• included=, in a reason as in
any member; in a reason it is grounds too.  A pointing link is a link in
the text, drawn there.  A reason whose words are the link, ~***
[[truss-include:m7]]~, is drawn as written, its role and m7's words.

A member keeps the words of its source with it, in a ~#+begin_quote~
block in its own text, which is written out as the quotation it is -- in
a comment block it stays in the file -- and gives it grounds; it may keep
several, each drawn in its text as a quotation of its own.  /edit/ on
the member writes one or rewrites it.  With
org-moor, reading a source beside it -- ~org-moor-noter~ -- writes the
quotation and the link to its page or line in one go.

A quotation is the source's words as they are, so the board looks for
it in the source: the one linked in the quotation, else the first the
member's text cites, else the first a member above it cites.  Line
breaks, spaces and full- or half-width letters are set aside, and words
left out are marked =…=; a word changed is not found.  It looks only
where the source's text can surely be read as the one who quoted it
read it: a replica that is text, or what org-moor made a slide deck, a page
or a document readable as.  A PDF, a picture, a file that does not read
cleanly -- raw bytes, or beyond ASCII in a coding of one byte a letter,
as a file in a coding Emacs did not guess is read -- is not looked in,
and nothing is said of a quotation from it: one said not to be found is
one that is not there.  Before its words, where the member's text is
drawn, the quotation is marked with which:

| Mark | Says                                                                     |
|------+--------------------------------------------------------------------------|
| =✓=  | found in the source                                                      |
| =✗=  | not found: listed under /Quotes not found/, below the division           |
| =?=  | not looked for: the source's text cannot surely be read, or none linked |

~org-truss-board-quote-marks~ sets them.  /Quotes not found/ is a
check of the report too (see [[*What is left to do]]), so an agent
working by ~org-truss-batch-check~ is told of it.

~m~, with org-moor, takes a source for the member as org-moor takes one,
into the truss file's ~sources/~, and writes the link to it on a line of
its own after the member's text -- for an item, at the end of its first
line, before its tags -- the reader's citation too: ~m w~ a page
or a file on the web, its replica fetched in the background
(~org-moor-take-url~); ~m f~ a file (~org-moor-take-file~); ~m c~ the
clipboard (~org-moor-take-clipboard~).  ~m l~ links a source the file
has, by its title, and ~m k~ keeps a replica, from their origins, of the
sources the member links to that have none -- those an agent took without
being able to fetch them as you, signed in (~org-moor-keep-replica~).  ~m o~
opens a source to check what a member says against it: on a link to a
source in a member's text, that source; on a quotation there, the source
it quotes, linked in it or else the first the text cites; elsewhere on a
member's lines, one its own text links to, asked for when there are
several.  The replica, at
the page or line the link names, as following the link does; ~m O~ where
it came from instead, the page on the web.  A link to anything but a
source org-moor took is followed as it is, with either.  A link put on a
comment line, ~# [[moor:...]]~, is the file's alone, and no ground.

A member is made to stand on another by a pointing link to it written
in its text, by hand, into a sentence the reader reads.  A member is tagged ~:assumption:~ with ~C-c C-q~, on a
heading or an item's first line alike.

/pattern/ works the same on every line with a member: on the /Structure/
line it gives the output document a pattern -- a telling pattern, Sky,
Rain, Umbrella, SCQA, PREP, with its members -- and on a member of
Structure the same for those under it; on the /Brief/ or the /Subject/
line, it changes what they are broken down into, and puts in a member for
each role none plays.  ~no logic~, ~no breakdown~ and ~no telling~ take
each off, and nothing is asked of what is below for it.

The foot of the board lists the commands with a key, as they are bound
where it is drawn, so a key moved or added -- by an Evil configuration,
say -- shows as it is, and a command with none is left off.

** Writing members from the board

A statement can be started without deciding where it goes.  /new/ asks for
its words, writes it, and opens it as /edit/ does, to be written; ~C-c
C-k~ there takes it away again.  It goes under the member the line at
point is:

- a member, or Brief, Subject or Message; on a missing role, playing that
  role, where the pattern lists it;
- on a member of Structure, at the end of Message, and included there by
  an include link;
- anywhere else, at the end of Message, where order means nothing.

Under an apex member, the new member plays a role in each of its
patterns: the one a pattern has alone -- a reason under reasons, a step
under steps -- without asking, and else the one asked for, those no
member plays yet first.  It goes where the patterns list the roles it
plays: before the first member there that plays one listed after its own,
or else last -- as /pattern/ puts in what a pattern asks for.

A member is moved in the file, by hand or by Org's ~C-c C-w~ and
~M-<up>~: links point to it by its ID, which goes with it, so Structure
still includes it wherever it goes.

Applying a telling pattern to a member of Structure that already has
members under it puts each, as it is, in the place of the new member
whose role it plays; the pattern adds members, named in
~org-truss-language~, only for the places none plays.  So switching
patterns changes the order and the marks, never a member's words.  A
member in none of the places is kept after the rest, and the board marks
it =[no role]=; /roles/, or the file, sorts it out.

* The output document

/view/ on the board shows the output document in another window without
writing it, and the board keeps it current while it is shown: the place
to read it.  Structure on the board, drawn whole, comes close but is not
the same.  Brief, what Structure does not include and the lists of what
is left to do are not in the output document, and on one line each line
shows only a title.

~M-x org-truss-export~, or ~x~ on the board, walks Structure and writes
what the reader sees to ~out/truss.org~ (~org-truss-output-directory~),
then runs pandoc, when it is installed, to make ~out/truss.md~.  Only
Structure is in it, and the trusses and members its include links reach.

- A member is its words (a heading, an item's first line), then its text;
  a comment is left out: a line starting with ~#~ and a space, or a
  ~#+begin_comment~ block.  A member tagged ~:noexport:~ is left out, with
  what is under it.
- The output document is titled by the file's ~#+title~; Structure's
  text opens it.
- A member of Structure is a heading of the output document; its text
  follows, the include links in it including what they include where they
  stand.
- Where an include link stands says the shape.  On a heading line, ~***
  [[truss-include:m7]]~, m7's words are that heading, and what is under it
  is written under headings a level down.  In text -- a member's text, a
  list item, a sentence -- its words are written in place and the rest
  follows the paragraph, or goes inside the list item, as a list one level
  in.  Once a list, what is under it stays a list.  Below the sixth level,
  Markdown's last, what is under a heading is a list.  A pointing link,
  ~[[m7]]~, is written as its description, or m7's words.
- The supporting members of a truss are written as what the truss is
  says, never as the file writes them, items or headings:

  | The truss                                       | Its supporting members        |
  |-------------------------------------------------+-------------------------------|
  | simple, of a ~TRUSS_LOGIC~ or ~TRUSS_BREAKDOWN~ | a list, under the apex member |
  | compound                                        | headings, a level down        |
  | of a ~TRUSS_TELLING~ alone, or of no pattern    | headings: a telling says only the order |

  So a heading of the output document is a claim, and the list below it
  what holds it up; where what holds it up are claims with reasons of
  their own, each is a heading, its list below it.  Steps are numbered,
  the rest bulleted, and where the pattern names its roles each opens
  with its own, /Who:/, /Pros:/ -- an item and a heading alike, /2. Ask
  them/.  A supporting member that is an include link alone is the
  member it includes here too: one including the facts of a source,
  ~[[truss-include:m20]]~, makes its truss compound, and is a heading,
  the facts a list under it.  ~TRUSS_AS~, or ~:as~ in ~#+attr_truss~,
  writes one truss's the other way (see [[*Writing members]]).
- Under an axis, each item opens with its value, /Under 100k:/, and a
  member whose words are none is its value.  Two axes are a table, when
  each row is its value alone and each cell a value and its words, with
  no text, members or include links: a row for each value of the one,
  a column for each of the other in the order first met, the corner
  naming both, /Amounts × stage/, and a cell empty where a row has none.
  Any other is told as a tree.  ~TRUSS_AS~ writes it as a list or as
  headings all the same.
- Once a list, what is under it stays a list, and so below the sixth
  level: a truss there that ~TRUSS_AS~ says to write as headings is a list
  all the same, and /Headings in a list/ finds it.
- A member written as an item stands where its list stands in its apex
  member's text: text after the list follows it, and the members written
  as headings come last, on the last list when no text follows it.  Where
  they would be headings of the output document, text after them makes
  them a list: Org has no text of a heading after the headings under it.
- An include link to no member is written as /(broken link: …)/, and one
  that would include without end as /(included without end: …)/, where it
  will be seen.
- A link to a file by a relative path -- a picture in ~attach/~, a source --
  is written relative to ~out/~, so the output document still finds it,
  and pandoc makes a picture an image.  /view/ shows the pictures where
  they are.
- A ~moor:~ link, with org-moor, goes where its source came from, since
  the replica in ~sources/~ is yours and the reader has none: to the page on
  the web, at the page the link names when it is a PDF,
  ~[[https://e.x/act.pdf#page=14][Act p. 14]]~.  A source that came from
  no such page -- a file, a mail -- is named by the link's words, or its
  title, as text.  The first link to a source in the output document,
  named by a place alone, ~l. 223~, has the source's title put before
  it, ~Manual l. 223~, so the reader is told which source wherever it
  is first cited; the links after it are as written.  /view/ keeps the
  link to the replica, to be followed in Emacs.

The language is that of what org-truss writes for you to read or to
rewrite: the guide, what ~?~ says, the members a pattern adds, and what

so a file reads the same to everyone.

* Batch

#+begin_src sh
emacs --batch -L . -L ../org-dock -L ../org-item-tags -l org-truss -f org-truss-batch-check  truss.org
emacs --batch -L . -L ../org-dock -L ../org-item-tags -l org-truss -f org-truss-batch-board  truss.org
emacs --batch -L . -L ../org-dock -L ../org-item-tags -l org-truss -f org-truss-batch-export truss.org
emacs --batch -L . -L ../org-dock -L ../org-item-tags -l org-truss -f org-truss-batch-guide
emacs --batch -L . -L ../org-dock -L ../org-item-tags -L ../org-moor -l org-truss -l org-moor \
      -f org-truss-batch-take truss.org FILE-OR-URL [TITLE]
#+end_src

The first prints what is left to do, as ~M-x org-truss-check~ lists it:
under the name of each check that finds something and what it finds, a
line for each thing, ~truss.org:42: …~.  Anything that edits the file
without the board -- you by hand, or a model working in the file -- can
run it to see what it broke or left undone.  The guide at the head of a
truss file gives this line, with the directories org-truss, org-dock and
org-item-tags are loaded from, and org-moor, when it is there, so that
~moor:~ links are checked too.

Any other Org file is checked as the board of one heading reads it: each
apex member with none above it.  A copy taken out by org-dock is checked
written back where it came from, so that its links, grounds and sources
are found as they will be: what is in the copy is given by the copy's
lines, and what is outside it only when the copy brings it about.  An
agent handed a copy is told to check it so, with its patterns, what its
heading plays in the pattern above it, and -- out of a truss file -- that
the rest of the rules are in the file's guide; the same words whichever
heading, or the whole file, was taken out.

The second prints the board as text, for anything that reads the
structure without Emacs open.  The fourth prints the guide, as the
drawer at a truss file's head holds it, and then what ~?~ says of each
division and of each role of Brief's and Message's breakdowns, in
~org-truss-language~.

The last, with org-moor, takes a file -- copied, never moved -- or a web
page into the truss file's ~sources/~ and prints a link to it named by its
title, for a model working in the file, which cannot ask Emacs: written
in a member's text, it cites the source.  The guide gives this line too
when org-moor is there.
